# AI 学情分析与智能学习平台项目设计文档

版本：1.0  
状态：第一期开发基线  
适用范围：Web 服务端与 Android 客户端  
更新日期：2026-09-16

## 1 文档目的

本文档作为正式版开发的统一技术基线。后端、Web 和 Android 均以本文档定义的业务边界、数据模型、接口契约、状态流转和验收标准实施。

项目分为两期：

- 第一期建设 AI 智能学习闭环，是当前开发重点。
- 第二期建设账号、鉴权、数据隔离和云端数据平台；第一期必须为第二期保留兼容接口，但不提前实现完整账号体系。

除经评审确认的变更外，开发过程中不得在客户端重复实现服务端业务规则，不得继续把正式练习数据仅存放在报告 JSON 中，也不得通过修改既有接口语义破坏已上线的 Android 和 Web 流程。

## 2 建设目标与范围

### 2.1 第一期目标

第一期在现有试卷上传、AI 分析、报告生成和 Android 客户端基础上，建立以下闭环：

```text
试卷采集
  -> 多模态学情分析
  -> 薄弱知识点与错因识别
  -> 生成结构化学习计划
  -> 生成基础题 同构题 迁移题
  -> 学生在线作答
  -> 自动批改与反馈
  -> 更新知识掌握度
  -> 动态选择下一道题或调整任务
```

第一期交付内容：

1. 学生档案与跨分析关联。
2. 结构化学习计划及每日任务。
3. 独立练习题库与题目版本管理。
4. 在线答题、自动批改、解析和错题重做。
5. 基于作答结果的递进式举一反三。
6. 知识点掌握度更新与学习进度展示。
7. Web、Android 与服务端统一接口。
8. AI 质量控制、失败降级、审计记录和验收测试。

### 2.2 第一期不包含

- 用户注册、登录、找回密码和正式 Token 刷新。
- 多角色权限、机构、班级和家长关系。
- 支付、会员、套餐和计费中心。
- PostgreSQL、对象存储和分布式任务队列的正式迁移。
- iOS、小程序和教师管理后台。
- 应用商店上架及短信验证码服务。

### 2.3 第二期目标

第二期在第一期领域模型之上增加用户身份、资源归属和正式云端基础设施，主要包括：

- 账号注册登录、会话管理和 Token 刷新。
- 接口级鉴权、资源级授权和用户数据隔离。
- 用户、学生档案、教师与机构关系。
- PostgreSQL 云数据库和对象存储。
- 跨设备同步、数据导出、注销删除和审计。
- 多用户任务队列、容量控制和运营监控。

## 3 现有系统基线

### 3.1 服务端

现有服务端采用 Next.js 16、React 19、TypeScript、Prisma 和 SQLite，已提供：

- 三种分析模式：单人单卷、单人多卷、多人同卷。
- 图片上传、页序控制、上传幂等和格式校验。
- 图像质检、文档分类、OCR、题目提取、答案评估、知识点映射、错因分析和报告规划。
- AI 输出 Schema 校验、上游限流退避、节点重试和失败降级。
- Job 锁、runToken、过期任务识别和全局容量限制。
- 题目人工复核、报告 JSON、HTML、PDF 和 PNG 导出。

### 3.2 Android

现有 Android 客户端采用 Kotlin、Jetpack Compose、Room、WorkManager、Retrofit、CameraX 和 DataStore，已提供：

- 相机、图库和 PDF 导入。
- 图片压缩、旋转、裁剪和页序调整。
- 后台上传、断网恢复、重试和任务状态轮询。
- 本地分析摘要与报告缓存。
- 报告浏览、下载和分享。

### 3.3 当前缺口

现有 `Question.aiPracticeQuestions` 仅适合报告展示，无法记录独立题目、作答历史和难度变化；报告建议也是静态内容，无法跟踪执行状态。因此第一期必须新增学习计划、练习会话、作答记录和掌握度等领域对象。

## 4 总体架构

### 4.1 系统分层

```text
Android App / Web
        |
        | HTTPS JSON API
        v
Next.js API 接入层
        |
        +-- 分析业务服务
        +-- 学习计划服务
        +-- 练习编排服务
        +-- 批改服务
        +-- 掌握度服务
        |
        +-- Prisma / SQLite 第一期
        +-- 私有文件存储 第一期
        |
        +-- OCR Provider
        +-- Vision Provider
        +-- Text Model Provider
```

### 4.2 责任边界

| 组件 | 负责内容 | 禁止承担 |
|---|---|---|
| 服务端 | 业务事实源、学习规则、AI 调用、批改、掌握度、版本与幂等 | 不依赖客户端保存唯一业务数据 |
| Android | 数据采集、交互、本地缓存、离线队列、状态展示 | 不自行决定题目升降级和掌握度 |
| Web | 分析复核、报告浏览、开发期学习闭环入口 | 不复制一套独立业务规则 |
| AI Provider | OCR、内容生成、主观题辅助评估 | 不直接修改数据库，不决定权限和状态流转 |

### 4.3 核心设计原则

1. 服务端是唯一事实源，Android Room 只做缓存和待同步队列。
2. 学习路径由确定性规则引擎控制，AI 只负责题目内容和主观题评估。
3. 所有生成结果必须经过结构化 Schema 校验后才能入库。
4. 创建类接口必须支持幂等；状态修改必须支持版本校验。
5. 现有分析和报告接口保持兼容，新能力通过新增接口和 capability 暴露。
6. 原始作答、AI 判定、人工复核必须分开保存，禁止覆盖证据链。
7. 第一阶段数据模型预留 `ownerId` 或归属扩展点，但业务不依赖登录态。

## 5 第一期功能设计

### 5.1 学生档案

第一期新增稳定的学生档案 `Learner`，用于关联多次分析、学习计划和掌握度。

- 支持创建、编辑和选择学生档案。
- 昵称、年级为基础字段，备注和教材版本可选。
- 新建分析时允许传入 `learner_id`。
- 旧客户端未传 `learner_id` 时仍可按现有流程创建分析，但不进入长期掌握度累计。
- 多人同卷模式中，每份作答可关联一个学生档案。

### 5.2 学习计划

分析完成并人工复核后，用户可生成学习计划。

- 默认周期为 7 天，可选 7 天、14 天。
- 计划从明确判定且证据充分的薄弱知识点中选取最多 3 个优先方向。
- 每日 1 至 3 个学习任务，每个任务包含知识点、目标难度、建议题量和达标条件。
- 学习计划生成后持久化保存，不随报告重新生成而静默覆盖。
- 重新生成必须创建新版本，旧版本保留为 `superseded`。
- 当报告中可用数据不足时，只生成复核或基础练习任务，不输出强结论。

### 5.3 递进式出题

每个薄弱知识点采用三级题目：

| 层级 | 名称 | 目的 | 生成约束 |
|---|---|---|---|
| 1 | 基础题 | 检查核心概念与基本步骤 | 单一知识点、低干扰、答案明确 |
| 2 | 同构题 | 改变数字、条件或表达形式 | 保持解法结构，不复制原题 |
| 3 | 迁移题 | 改变情境或组合方式 | 不超出年级、学期和教材范围 |

每道题必须保存题干、题型、难度、知识点、参考答案、解析、生成来源、模型版本和内容版本。题目生成失败不得阻塞已生成题目的使用。

### 5.4 在线作答与批改

- 客观题优先使用确定性规则批改，包括标准化空格、大小写和数值格式。
- 主观题由 AI 给出 `correct`、`partial`、`wrong` 或 `needs_review`，并返回简短反馈和置信度。
- 低置信度、无标准答案或输出校验失败时进入 `needs_review`，不更新掌握度。
- 用户提交后先保存原始答案，再执行批改；批改失败可独立重试。
- 参考答案默认在提交后展示，避免提前泄露。
- 每次作答形成独立记录，不覆盖历史作答。

### 5.5 自适应举一反三

第一期采用可测试的规则引擎：

1. 新知识点默认从基础题开始；已有掌握度可决定初始层级。
2. 同一层级连续 2 题正确后升级。
3. `partial` 保持当前层级并追加 1 题。
4. `wrong` 降低一个层级；已在基础层级则提供提示后重试。
5. 连续 2 题错误时暂停自动升级，任务标记为需复习。
6. 单个任务最多 8 次有效作答，防止无限生成。
7. AI 生成失败时优先使用已缓存题目；无题可用时返回可重试状态。

规则阈值集中配置，不允许散落在 Android 或多个 API Route 中。

### 5.6 掌握度

每个学生、学科和知识点维护一条当前掌握度记录，并保留快照。

- 分值范围为 0 至 100。
- 初始值来自最近分析中明确判定的题目，不使用 `unknown` 或待复核题目。
- 练习作答按照题目层级和判定结果增减分值。
- 单次练习对掌握度的变化设置上限，避免少量题目造成剧烈波动。
- 人工复核结果优先级高于模型判定。
- 每次变化记录来源、旧值、新值和原因，支持解释和回溯。

## 6 核心业务流程

### 6.1 分析到学习计划

1. Android 创建分析并上传图片。
2. 服务端完成 AI Pipeline，报告状态变为 `ready`。
3. 用户完成必要的人工复核。
4. 客户端请求生成学习计划，并携带幂等键。
5. 服务端选取证据充分的薄弱知识点，生成计划与首批练习题。
6. 计划进入 `active`，客户端展示今日任务。

### 6.2 练习会话

1. 客户端从学习任务创建练习会话。
2. 服务端依据当前掌握度返回第一道题。
3. 客户端提交 `client_attempt_id` 和答案。
4. 服务端保存答案并返回批改状态。
5. 完成批改后更新题目结果、任务进度和掌握度。
6. 规则引擎决定结束、保持、降级或升级，并返回下一题。

### 6.3 失败恢复

- Android 将未完成提交保存在 Room 队列中。
- 相同 `client_attempt_id` 重试只产生一次作答记录。
- 批改失败保留 `submitted` 状态，可由服务端或客户端触发重试。
- 会话恢复时以服务端返回的 `version` 和 `next_question` 为准。

## 7 数据模型

### 7.1 新增核心实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Learner | id nickname grade curriculumVersion status createdAt updatedAt | 稳定学生档案 |
| LearningPlan | id learnerId sourceAnalysisId cycleDays status version generatedAt | 学习计划主表 |
| LearningTask | id planId knowledgePoint title targetLevel targetCount completedCount status dueDate order | 每日或阶段任务 |
| PracticeQuestion | id sourceQuestionId subject grade knowledgePoint level type content referenceAnswer explanation status version | 独立练习题 |
| LearningTaskQuestion | taskId questionId order | 计划任务与题目关联 |
| PracticeSession | id learnerId taskId status currentLevel version startedAt completedAt | 一次连续练习会话 |
| PracticeAttempt | id sessionId questionId clientAttemptId answer status gradingStatus result confidence feedback submittedAt gradedAt | 单次作答记录 |
| KnowledgeMastery | id learnerId subject knowledgePoint score evidenceCount version updatedAt | 当前掌握度 |
| MasterySnapshot | id masteryId sourceType sourceId previousScore newScore reason createdAt | 掌握度审计记录 |

### 7.2 现有实体调整

| 实体 | 调整内容 |
|---|---|
| Analysis | 新增可空 `learnerId`；保留原有 `studentNickname` 作为分析快照，避免档案修改影响历史报告 |
| Paper | 新增可空 `learnerId`，用于多人同卷模式关联具体学生 |
| Question | 保留 `aiPracticeQuestions` 用于旧报告兼容；新生成题同步写入 `PracticeQuestion`，后续不再以 JSON 作为业务事实源 |
| AiRun | 扩展 `contextType`、`contextId`，支持分析、计划生成、练习出题和主观题批改的统一审计 |

### 7.3 关键唯一约束

- `PracticeAttempt.clientAttemptId` 全局唯一。
- 同一计划版本内任务顺序唯一。
- 同一学生、学科、知识点仅有一条当前 `KnowledgeMastery`。
- 同一来源题、知识点、层级和内容版本不得重复生成等价题目。
- 计划和会话的状态修改使用 `version` 做乐观并发控制。

## 8 API 契约

第一期 API 契约版本升级为 `3.0.0`。原有 2.1.0 接口保持兼容，健康检查新增 capability：

```json
{
  "learning_plans": true,
  "practice_sessions": true,
  "adaptive_practice": true,
  "learner_profiles": true
}
```

### 8.1 学生档案

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/learners` | 创建学生档案，要求 Idempotency-Key |
| GET | `/api/learners` | 获取学生列表 |
| GET | `/api/learners/{id}` | 获取学生详情与摘要 |
| PATCH | `/api/learners/{id}` | 修改档案，携带 version |
| GET | `/api/learners/{id}/mastery` | 获取知识点掌握度 |
| GET | `/api/learners/{id}/history` | 获取分析、计划和练习历史 |

### 8.2 学习计划

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/analyses/{id}/learning-plans` | 从分析生成计划，要求 Idempotency-Key |
| GET | `/api/learning-plans/{id}` | 获取计划和任务 |
| POST | `/api/learning-plans/{id}/regenerate` | 生成新版本，不覆盖旧版本 |
| PATCH | `/api/learning-tasks/{id}` | 更新任务状态，携带 version |

生成计划请求示例：

```json
{
  "cycle_days": 7,
  "daily_task_limit": 2,
  "question_count_per_task": 5
}
```

### 8.3 练习会话与作答

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/learning-tasks/{id}/sessions` | 创建或恢复练习会话 |
| GET | `/api/practice-sessions/{id}` | 获取会话状态、进度和下一题 |
| POST | `/api/practice-sessions/{id}/attempts` | 提交答案，要求 client_attempt_id |
| POST | `/api/practice-attempts/{id}/retry-grading` | 重试失败批改 |
| POST | `/api/practice-sessions/{id}/complete` | 结束会话并结算任务进度 |

作答提交请求示例：

```json
{
  "client_attempt_id": "uuid",
  "question_id": "practice-question-id",
  "answer": "用户原始答案",
  "session_version": 3
}
```

作答响应至少包含：

```json
{
  "attempt_id": "id",
  "grading_status": "graded",
  "result": "correct",
  "feedback": "计算过程正确",
  "mastery": { "before": 52, "after": 58 },
  "session": { "status": "active", "level": 2, "version": 4 },
  "next_question": {}
}
```

### 8.4 通用错误码

| HTTP | error | 处理方式 |
|---:|---|---|
| 400 | validation_error | 客户端提示并保留输入 |
| 404 | not_found | 返回上级页面并刷新缓存 |
| 409 | version_conflict | 重新拉取服务端状态 |
| 409 | idempotency_conflict | 禁止换参数复用幂等键 |
| 422 | grading_unavailable | 标记待复核，不更新掌握度 |
| 429 | rate_limited | 遵守 Retry-After |
| 503 | server_busy | 延迟重试，不重复创建业务记录 |

## 9 服务端实现设计

### 9.1 模块划分

建议新增：

```text
lib/learning/
  plan-service.ts
  practice-service.ts
  grading-service.ts
  mastery-service.ts
  adaptive-policy.ts
  schemas.ts
  types.ts
```

- Route Handler 只负责认证预留、参数校验、调用服务和响应映射。
- Prisma 写操作通过事务保证作答、掌握度和任务进度一致。
- `adaptive-policy.ts` 只包含纯函数规则，并使用单元测试覆盖全部分支。
- AI Provider 新增计划生成、练习题生成和主观题评估节点。
- 计划生成和批改的原始输入输出记录到扩展后的 `AiRun`。

### 9.2 AI 节点

| 节点 | 输入 | 输出 | 失败策略 |
|---|---|---|---|
| learning_plan | 已复核题目、统计、教材范围 | 结构化计划草案 | 使用规则模板生成基础计划 |
| practice_generation | 原题、知识点、层级、年级 | 练习题、答案、解析 | 重试后使用缓存题 |
| practice_grading | 题目、参考答案、学生答案 | 结果、反馈、置信度 | 标记 needs_review |

### 9.3 数据一致性

一次批改完成事务应包含：

1. 锁定或校验会话版本。
2. 更新 `PracticeAttempt`。
3. 更新 `KnowledgeMastery`。
4. 写入 `MasterySnapshot`。
5. 更新 `LearningTask.completedCount`。
6. 运行自适应规则并更新 `PracticeSession`。

AI 网络请求不得放在长数据库事务中。应先保存提交记录，再执行 AI，最后使用短事务落库。

### 9.4 兼容和迁移

- Prisma 迁移只能增量执行，不删除现有分析、报告和图片。
- 现有 `aiPracticeQuestions` 不立即删除。
- 报告中的旧练习题可在首次生成计划时导入为 `PracticeQuestion`。
- 旧 Android 仍可只使用分析和报告功能。
- `GET /api/health` 用 capability 告知新客户端是否开放学习功能。

- `cached_practice_sessions`
- `pending_practice_attempts`

计划、任务和服务端题目可以缓存；参考答案仅在服务端已允许展示后缓存。待提交答案必须保存 `clientAttemptId`，应用重启后继续复用同一编号。

### 10.4 状态管理

- ViewModel 使用 `StateFlow` 输出不可变 UI State。
- 提交按钮在本地排队成功后立即禁止重复点击。
- 网络恢复由 WorkManager 处理待提交作答。
- 收到 `version_conflict` 时重新获取会话，不自动覆盖本地输入。
- 退出练习不等于结束会话，用户可继续未完成会话。

### 10.5 安全与隐私

第一期不在 APK 中保存 AI Provider Key。正式答案、解析和学生作答不得写入普通日志。第二期接入账号后，Token 使用加密存储并按用户清理 Room 缓存。

## 11 状态定义

### 11.1 学习计划

```text
draft -> generating -> active -> completed
                    -> failed
active -> paused -> active
active -> superseded
```

### 11.2 学习任务

```text
pending -> active -> completed
               -> needs_review
pending/active -> skipped
```

### 11.3 练习会话

```text
active -> completed
       -> abandoned
       -> blocked
```

### 11.4 作答批改

```text
submitted -> grading -> graded
                     -> needs_review
                     -> failed -> grading
```

所有状态值由服务端统一定义，Android 需要保留未知状态兼容分支，不能因新增枚举值崩溃。

## 12 非功能要求

### 12.1 性能

- 普通查询接口目标响应时间不超过 1 秒。
- 创建会话和提交客观题目标响应时间不超过 2 秒。
- AI 出题和主观题批改允许异步完成，客户端显示处理中状态。
- 单次会话最多预取 3 道题，避免无效 AI 成本。

### 12.2 稳定性

- 所有创建和提交接口具备幂等性。
- AI 调用沿用现有 Provider 超时、限流识别和退避机制。
- 服务端重启后已提交作答可继续批改。
- Android 进程被系统回收后可恢复当前会话和待提交答案。

### 12.3 AI 质量

- 生成题不得直接复制原题。
- 题目、答案和解析必须通过 Zod Schema 校验。
- 数学题应执行基础一致性检查；无法验证时标记待抽检。
- 主观题低置信度不得直接改变掌握度。
- 结论必须绑定来源分析、原题或练习作答。

### 12.4 可观测性

记录以下指标：

- 计划生成成功率和耗时。
- 练习题生成成功率、重试次数和模型成本。
- 批改成功率、待复核率和人工改判率。
- 会话完成率、平均作答数和知识点提升量。
- 关键 API 错误率、503 和 429 次数。

## 13 开发计划与职责

第一期计划工期 30 个工作日，由两名开发人员协同完成。建议按领域分工而不是简单按端完全切割。

| 阶段 | 工作日 | 服务端主责 | Android 主责 | 联合交付 |
|---|---:|---|---|---|
| 设计冻结 | 1 至 3 | 数据模型、API、迁移方案 | 页面流、缓存模型 | 契约评审与样例 JSON |
| 领域基础 | 4 至 9 | Learner、Plan、Task、Question 模型与接口 | 新模型、Room 迁移、Repository | 学生与计划联调 |
| 练习闭环 | 10 至 17 | Session、Attempt、批改和自适应规则 | 练习页、提交队列、结果页 | 客观题完整链路 |
| AI 与掌握度 | 18 至 23 | 出题、主观题评估、掌握度事务 | 处理中、待复核和恢复体验 | AI 链路验收 |
| 集成与兼容 | 24 至 27 | 报告入口、旧数据导入、能力协商 | 首页、报告入口、旧版兼容 | 公网环境联调 |
| 测试与发布 | 28 至 30 | 迁移、监控、回归、发布 | 真机测试、离线恢复、Release 构建 | 验收与文档 |

API Schema、状态枚举或数据库字段调整必须同时通知双方；禁止一端先行改变契约后要求另一端通过容错猜测适配。

## 14 测试与验收标准

### 14.1 服务端测试

- 自适应规则纯函数单元测试覆盖升级、保持、降级、封顶和异常分支。
- API 测试覆盖幂等、版本冲突、重复提交、批改失败和恢复。
- 数据迁移测试验证现有 Analysis、Question、Report 和图片不丢失。
- AI Schema 测试覆盖非法输出、空题、超纲内容和低置信度。

### 14.2 Android 测试

- Repository 映射和未知枚举兼容测试。
- Room 迁移测试。
- 重复点击不会产生重复作答。
- 断网提交、恢复网络、应用重启后可继续同步。
- 小屏幕、大字体和 Android 8 以上真机可用。

### 14.3 第一期验收条件

1. 可从一份已完成分析生成 7 天学习计划。
2. 学习计划至少包含 2 个结构化任务和明确达标标准。
3. 每个任务能够生成并完成基础题、同构题和迁移题流程。
4. 客观题可自动判定；主观题可返回判定或进入待复核。
5. 重复提交同一 `client_attempt_id` 不产生重复记录。
6. 完成练习后掌握度、任务进度和会话状态保持一致。
7. Android 断网和重启后可恢复未完成练习。
8. 旧版本 Android 的分析、报告和导出功能不受影响。
9. Web 与 Android 对同一计划和会话显示一致。
10. 公网正式环境完成至少一条真实分析到练习闭环验收。

## 15 第二期兼容设计

第一期开发时必须遵守以下预留：

- 新表统一使用字符串主键、创建时间、更新时间和版本字段。
- 业务查询集中在服务层，避免 Route 内直接拼接无归属条件的查询。
- Learner、Analysis、Plan、Session 和文件资产保留未来 `ownerId` 或 `tenantId` 接入位置。
- Android 缓存实体以服务端 ID 为主键，方便第二期按账号清理和重新同步。
- API 客户端统一支持可选 Authorization Header，但第一期不在 APK 内置生产凭据。
- 文件读取统一经过存储抽象，避免第二期迁移对象存储时修改业务层。
- 第二期上线后，所有资源查询必须同时校验资源 ID 与当前用户归属。

第二期预计将 API 契约升级为 `4.0.0`，账号认证属于破坏性边界变化，Android 必须在启动时完成能力与最低版本检查。

## 16 变更管理

本文档为第一期开发基线。出现以下情况时必须先更新文档和接口样例，再修改代码：

- 增删核心实体或改变字段语义。
- 修改自适应升级、降级或掌握度规则。
- 修改计划、任务、会话或作答状态。
- 修改 API 路径、错误码或幂等行为。
- 改变服务端与 Android 的责任边界。

每次正式变更应记录版本、日期、影响范围和迁移方式，确保后端、Web、Android 和部署配置保持一致。
